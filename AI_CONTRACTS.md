# AI Collaboration Contracts

This document is the shared technical agreement for all Codex agents working on Prep. `PLAN.md` defines the product scope; this file defines the interfaces and working boundaries needed to implement it safely.

## 1. Shared Delivery Contract

- Build only the MVP in `PLAN.md`.
- Use **Next.js + TypeScript + Tailwind CSS**, **Supabase**, and **Vercel**.
- Keep the application deployable from `main`.
- Do not introduce a separate custom backend or expose a Supabase service-role key. The browser uses the Supabase anon key and Supabase Row Level Security protects data.
- Every task must state its changed files, validation performed, and any setup step another agent must complete.

## 2. Ownership Contract

| Area | Owner | May change |
| --- | --- | --- |
| App interface | Frontend agent | `app/`, `components/`, client-side UI helpers, styles |
| Data and security | Backend agent | `supabase/`, migrations, RLS policies, Supabase configuration |
| Integration and release | Integration/QA agent | `.env.example`, tests, deployment documentation, CI configuration |

- Do not modify another area without first describing the dependency in the pull request or issue.
- Shared interfaces in this document require agreement from the affected owners before they are changed.

## 3. Product and Data Contract

The MVP has one shared room. There is no `rooms` table or direct-message model in version one.

### `profiles`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | `uuid` | Primary key; references `auth.users.id` |
| `display_name` | `text` | Required; 2–30 visible characters |
| `created_at` | `timestamptz` | Required; defaults to the current time |

### `messages`

| Column | Type | Rule |
| --- | --- | --- |
| `id` | `uuid` | Primary key; generated by the database |
| `sender_id` | `uuid` | Required; references `profiles.id` |
| `body` | `text` | Required after trimming; 1–2,000 characters |
| `created_at` | `timestamptz` | Required; defaults to the current time |

### TypeScript Interface

```ts
export interface Profile {
  id: string;
  display_name: string;
  created_at: string;
}

export interface Message {
  id: string;
  sender_id: string;
  body: string;
  created_at: string;
  sender: Pick<Profile, "id" | "display_name">;
}
```

The frontend displays messages in ascending `created_at` order. On entry it loads the newest 100 messages, then presents those messages oldest to newest.

## 4. Authentication and Security Contract

- Sign in is email magic link only.
- Supabase Auth invitations create the three approved accounts. Public registration is disabled.
- A signed-in user without a profile must complete profile setup before opening the chat.
- Authenticated users may read `profiles` and `messages`.
- A user may insert a profile only with `id = auth.uid()` and update only their own profile.
- A user may insert a message only with `sender_id = auth.uid()`.
- The MVP permits no message updates or deletes.
- Enable Supabase Realtime only for inserts on `messages`.

## 5. Frontend Integration Contract

- Use one shared browser Supabase client module; do not create ad-hoc clients throughout components.
- Keep Supabase URL and anon key in `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` only. Add their names, not values, to `.env.example`.
- The chat screen must subscribe to new `messages` inserts and de-duplicate messages by `id`.
- Client validation must match the database constraints, but the database remains the final authority.
- Show a clear error state for failed magic-link requests, profile saves, message loads, and message sends.

## 6. Git and Handoff Contract

- One focused task per branch and pull request; do not commit directly to `main`.
- Rebase or merge the latest `main` before handing off work and resolve conflicts in the files you changed.
- Do not commit secrets, generated dependency folders, or unrelated formatting changes.
- Before review, run the relevant type check, lint, tests, and a manual responsive check when UI changed.
- A handoff note must include: summary, files changed, commands run, unresolved risks, and required Supabase/Vercel actions.

## 7. Non-Goals

Do not implement direct messages, multiple rooms, file uploads, reactions, edit/delete, typing indicators, read receipts, notifications, or an in-app team-administration screen unless the team updates `PLAN.md` and this contract.
